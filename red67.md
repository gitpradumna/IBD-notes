# Week 6 Assignment — SparkSQL on Google Cloud Dataproc

## 1. Project overview

This assignment uses **Apache SparkSQL on Google Cloud Dataproc** to analyse transaction data and implement two Slowly Changing Dimension (SCD) strategies for customer master data:

- **SCD Type I:** update customer attributes in place, retaining only the latest version.
- **SCD Type II:** preserve the previous customer record as history and insert a new current record when a tracked attribute changes.

The workflow also produces three transaction-analysis results: the top five customers by transaction value, the number of distinct customers represented in each transaction city, and the overall average transaction value.

The Python file is the Spark application entry point. It creates a Spark session and executes the data preparation, transformations, aggregations, SCD operations, validations, and output writes through **SparkSQL statements**. The job is submitted to the Dataproc cluster as a PySpark job because the entry-point file is Python; the data transformations themselves are written in SQL rather than the PySpark DataFrame API.

## 5. Processing approach

The processing pipeline follows the sequence below.

1. **Create the Spark session.** The Python driver starts a Spark application with the name `Week6_SparkSQL_SCD_Analysis`.
2. **Register the input CSV files.** SparkSQL `CREATE OR REPLACE TEMPORARY VIEW ... USING csv OPTIONS (...)` statements register the three Cloud Storage CSV files as temporary views: `transactions`, `customer_master`, and `customer_updates`.
3. **Run transaction aggregations.** SQL statements calculate the top five customers by total transaction amount, distinct customers per transaction city, and the average transaction value.
4. **Prepare the customer master baseline.** SQL views cast the date and flag columns to appropriate types for the SCD operations.
5. **Apply SCD Type I.** A SQL `FULL OUTER JOIN` combines the current master data with the updates. `COALESCE` selects the updated attribute when one is supplied and otherwise retains the existing attribute. The result represents the latest customer state without keeping the replaced version as history.
6. **Apply SCD Type II.** SQL joins and `UNION ALL` statements retain unchanged records, expire previous active records when tracked attributes change, and insert new current records for the changed customers.
7. **Write outputs to Cloud Storage.** SQL `INSERT OVERWRITE DIRECTORY ... USING csv OPTIONS ('header' = 'true') SELECT ...` statements write the result datasets to their respective output directories.
8. **Run SQL validations.** The application writes validation results, including row counts and per-customer version counts, to the `output/validation/` location in Cloud Storage when using the revised script containing those validation statements.

### Why the job type is PySpark

The Dataproc job is submitted as **PySpark** because `week6.py` is a Python file that creates the Spark session and invokes SQL through `spark.sql(...)`. This describes the application entry-point format. The transformations and data-processing logic are expressed as SparkSQL queries. The script does not use PySpark DataFrame transformation methods such as `select()`, `filter()`, `groupBy()`, `join()`, `withColumn()`, or DataFrame-based `write` operations.

## 6. SCD logic and date handling

The customer updates have a change date of **23 October 2025**. For a changed customer in SCD Type II:

- The previous version is marked historical with `current_flag = 0`.
- Its expiry date is set to **22 October 2025**, the day before the new version becomes effective.
- The new version receives an effective date of **23 October 2025**, `current_flag = 1`, and a `NULL` expiry date.

The validity dates therefore use an inclusive-date convention without overlapping the old and new versions.

The Type II comparison checks the tracked attributes `customer_name`, `city`, and `dob`. A new version is created when at least one of these attributes differs. Consequently, all five customers represented in the update file can receive a new Type II version even though only some customer names change.

In the supplied update data, the customer names change for **c002** and **c007** only. The other updated customers have changes to city and/or date of birth while retaining their original names. The `_Upd` suffix is therefore present only where the input name itself contains that suffix; it is not added artificially by the SCD logic.

## 9. Errors encountered and corrections

During development, two job attempts required correction:

- **Exit code 143:** an earlier run was terminated. The cluster diagnostics suggested possible memory pressure, so the Spark driver/executor memory and parallelism settings were made explicit for the subsequent run. Exit code 143 alone does not conclusively establish an out-of-memory failure.
- **Unresolved column error:** an earlier SCD query referred to a column named `status`, which did not exist in the supplied update CSV. The query was corrected to use the actual input columns, including `dob` and `change_date`.

The corrected application completed successfully in the recorded successful run. When preparing the final ZIP, ensure that `week6.py`, the seven CSV outputs, and `execution_log.png` all correspond to the final revised successful run.
